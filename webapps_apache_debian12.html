Apache como servidor de aplicaciones

Referencia de laboratorio · Administración y Configuración Cliente/Servidor · Del esquema LAMP a Tomcat

Un servidor web recibe peticiones HTTP y entrega archivos: una página HTML, una imagen, una hoja de estilos. El archivo sale del disco tal como está. Un servidor de aplicaciones va un paso más allá: en lugar de entregar el archivo, ejecuta el código de la aplicación, consulta la base de datos, maneja sesiones de usuario y genera la respuesta en ese momento.

Apache nació como servidor web, pero en el esquema LAMP (Linux, Apache, MySQL/MariaDB, PHP) cumple también el papel de servidor de aplicaciones. El módulo libapache2-mod-php integra el intérprete de PHP dentro del propio Apache: cuando llega una petición a un archivo .php, Apache no lo entrega como texto, sino que lo ejecuta y devuelve el resultado. WordPress, PrestaShop y Moodle son aplicaciones PHP completas que funcionan de esta forma.

En Java la separación es más clara. Las aplicaciones Java no se ejecutan dentro de Apache, sino en un servidor de aplicaciones dedicado como Tomcat: un proceso de Java que permanece en memoria, carga la aplicación una vez y atiende las peticiones con servlets y páginas JSP. En producción es común poner Apache al frente como proxy, para que reciba las peticiones y se las pase a Tomcat.

Esta guía trabaja con Apache en su papel de servidor de aplicaciones PHP, instalando tres aplicaciones en el mismo servidor, en el orden del laboratorio: WordPress, PrestaShop y Moodle. Los conceptos que aparecen aquí (dónde se colocan las aplicaciones, qué ruta de URL les corresponde, quién es dueño de los archivos) se repiten después con Tomcat.

Lenguaje
Apache (LAMP): PHP · Tomcat: Java (servlets y JSP)
Cómo ejecuta
Apache: el módulo PHP interpreta cada petición · Tomcat: la aplicación queda cargada en la JVM
Dónde van las apps
Apache: /var/www/html · Tomcat: carpeta webapps
Cómo se instala una app
Apache: copiar la carpeta · Tomcat: desplegar un archivo .war
Puerto HTTP
Apache: 80 · Tomcat: 8080
Puerto HTTPS
Apache: 443 · Tomcat: 8443

Si una app no abre

Antes de cambiar cualquier cosa, lee la bitácora de errores: sudo tail -n 30 /var/log/apache2/error.log. Casi siempre dice exactamente qué falta: una extensión de PHP, un permiso o un error de sintaxis.

1. Conceptos

1.1

/var/www vs /var/www/html

Qué carpeta publica Apache y cuál solo guarda archivos.

/var/www/html
Es el DocumentRoot del sitio por defecto, definido en /etc/apache2/sites-available/000-default.conf. Todo lo que pongas aquí se publica en la URL automáticamente.
/var/www
Carpeta base. Apache tiene permiso de leerla, pero no la publica. Una app aquí solo es accesible si la conectas con un Alias o un VirtualHost.
/var/www/html/wordpress → http://localhost/wordpress /var/www/html/prestashop → http://localhost/prestashop /var/www/moodle/public → http://localhost/moodle (solo con Alias, ver 1.4)

Por eso WordPress funcionó con solo copiarlo a html: la ruta de la carpeta se convierte en la ruta de la URL.

1.2

sites · conf · mods

Las tres familias de configuración de Apache en Debian.

sites-available/
Sitios completos (VirtualHost). Aquí vive 000-default.conf. Se activan con a2ensite.
conf-available/
Fragmentos de configuración general que se suman a todos los sitios. Se activan con a2enconf.
mods-available/
Módulos que agregan funciones a Apache (rewrite, php, ssl). Se activan con a2enmod.
*-enabled/
Lo que está activo. Contiene solo enlaces simbólicos hacia *-available. Nunca se edita a mano.

La idea es que *-available es el catálogo y *-enabled es lo que está encendido. Los comandos a2en* y a2dis* solo crean o borran el enlace; el archivo original no se toca.

1.3

.htaccess

Un archivo de configuración de Apache que vive dentro de la carpeta de la aplicación.

Normalmente la configuración de Apache está en /etc/apache2 y solo la puede cambiar el administrador. El archivo .htaccess permite que cada aplicación traiga sus propias reglas dentro de su carpeta, sin tocar la configuración del servidor.

Nombre
empieza con punto, así que en Linux es un archivo oculto: no aparece con ls, sí con ls -a.
Alcance
sus reglas aplican a la carpeta donde está y a todas sus subcarpetas.
Cuándo se lee
Apache lo lee en cada petición. Un cambio en .htaccess aplica al instante, sin reiniciar Apache.
Requisito
solo funciona si la carpeta tiene AllowOverride All (paso 3.1). Con None, Apache lo ignora como si no existiera.
Quién lo usa
WordPress y PrestaShop lo crean al instalarse para sus URLs amigables. Moodle 5.1+ no lo usa: todo va en su archivo .conf.
$ls -a /var/www/html/wordpress

El -a muestra los archivos ocultos; ahí aparece .htaccess.

$cat /var/www/html/wordpress/.htaccess

Ver su contenido.

Ejemplo: el .htaccess de WordPress

# /var/www/html/wordpress/.htaccess# BEGIN WordPress
<IfModule mod_rewrite.c>
RewriteEngine On
RewriteBase /wordpress/
RewriteRule ^index\.php$ - [L]
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule . /wordpress/index.php [L]
</IfModule>
# END WordPress

WordPress lo genera solo al guardar Ajustes › Enlaces permanentes.

IfModule
aplica las reglas solo si mod_rewrite está activo; si no, las salta sin marcar error.
RewriteEngine On
enciende la reescritura de URLs para esta carpeta.
RewriteBase
la ruta de URL de la app: /wordpress/.
RewriteCond !-f · !-d
condiciones: «si lo que piden NO es un archivo real y NO es una carpeta real…»
RewriteRule
«…entonces mándalo a index.php». Así /wordpress/mi-primer-post lo resuelve WordPress, aunque no exista esa carpeta.

Ventaja: cada app se configura sola. Desventaja: Apache tiene que buscar y leer .htaccess en cada carpeta, en cada petición, y eso lo hace un poco más lento. Por eso en servidores grandes las reglas se pasan a los archivos .conf y se deja AllowOverride None, como hace Moodle.

1.4

Alias

Una directiva de Apache que conecta una ruta de URL con una carpeta del disco.

Sin Alias, la URL depende de dónde esté la carpeta: solo lo que está dentro del DocumentRoot (/var/www/html) tiene URL. El Alias rompe esa regla: le dice a Apache «cuando pidan esta ruta, busca los archivos en esta otra carpeta», aunque esté fuera de html.

# SintaxisAlias /ruta-en-la-url /carpeta/en/el/disco
Petición: http://localhost/moodle/login/index.php Alias: /moodle → /var/www/moodle/public Archivo: /var/www/moodle/public/login/index.php
Lo que cambia
solo la parte de la URL que coincide con el alias (/moodle) se sustituye por la carpeta. El resto de la ruta se conserva igual.
Va en pareja
el Alias abre el camino, pero la carpeta destino también necesita su bloque <Directory> con Require all granted. Sin él, Apache responde 403 Prohibido.
Módulo
lo da mod_alias, que Debian trae activado de fábrica.
Uso típico
publicar una app sin moverla a html. Debian mismo lo usa: phpMyAdmin se publica con Alias /phpmyadmin y los iconos de Apache con Alias /icons/.

¿Por qué no copiar la app a html y listo? Porque así solo se publica la carpeta que tú eliges. En Moodle 5.1+ se publica únicamente public, y config.php y el resto del código quedan fuera del alcance del navegador (paso 6.3).

2. Preparar el servidor

2.1

Instalar PHP y extensiones

Una sola vez, para las tres apps. WordPress pide pocas; PrestaShop y Moodle piden más.

$sudo apt update
$sudo apt install -y apache2 libapache2-mod-php php-mysql php-intl php-zip php-gd php-curl php-mbstring php-xml php-soap php-bcmath unzip
php-mysql
conexión a MariaDB/MySQL (las tres apps)
php-intl
idiomas, monedas y formatos regionales (PrestaShop y Moodle)
php-zip
instalar módulos, plugins y temas empaquetados
php-gd
procesar imágenes: miniaturas de productos, fotos de perfil
php-curl
conectarse a otros servidores: actualizaciones, pagos
php-mbstring
texto con acentos y ñ sin corromperse
php-xml · soap
importar/exportar datos y servicios web (Moodle)
php-bcmath
cálculos decimales precisos (precios en PrestaShop)
2.2

Verificar PHP

Confirmar la versión y que las extensiones cargaron.

$php -v

Debian 12 trae PHP 8.2.

$php -m | grep -Ei 'intl|zip|gd|curl|mbstring|xml|soap|bcmath|mysql'

Debe aparecer cada extensión de la lista anterior.

2.3

Crear una base de datos por app

Cada app necesita su propia base y su propio usuario. Repite este paso para cada una.

$sudo mysql -e "CREATE DATABASE nombre_bd CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; CREATE USER 'usuario_app'@'localhost' IDENTIFIED BY 'Contraseña_Segura1'; GRANT ALL PRIVILEGES ON nombre_bd.* TO 'usuario_app'@'localhost'; FLUSH PRIVILEGES;"
wordpress
base wordpress · usuario wp_user
prestashop
base prestashop · usuario ps_user
moodle
base moodle · usuario moodle_user

Cambia nombre_bd, usuario_app y la contraseña antes de ejecutarlo. Anota los datos: el instalador de cada app te los va a pedir.

3. Configuración general de Apache

Se hace una sola vez. Después, cualquier app que copies a /var/www/html queda en localhost/<carpeta> sin tocar Apache.

3.1

Crear webapps.conf

Un solo bloque que sirve para todas las apps que pongas en /var/www/html.

$sudo nano /etc/apache2/conf-available/webapps.conf
# /etc/apache2/conf-available/webapps.conf<Directory /var/www/html>
    Options -Indexes +FollowSymLinks
    AllowOverride All
    Require all granted
</Directory>

Contenido del archivo. Guarda con Ctrl+O y sal con Ctrl+X.

Qué hace cada línea

<Directory ruta>
Abre un bloque de reglas para esa carpeta. Las reglas se heredan a todas sus subcarpetas: por eso un solo bloque para html cubre wordpress, prestashop y cualquier app futura.
Options
Enciende (+) o apaga (−) características de Apache para esa carpeta.
-Indexes
Si una carpeta no tiene index.php o index.html, Apache no muestra la lista de archivos. Evita que alguien vea respaldos, logs o archivos de configuración navegando carpetas.
+FollowSymLinks
Permite seguir enlaces simbólicos. Además es requisito de mod_rewrite para que funcionen las reglas de los .htaccess.
AllowOverride All
Permite que el archivo .htaccess de cada app cambie la configuración de su carpeta. Debian trae None, que hace que Apache ignore los .htaccess. WordPress y PrestaShop traen su propio .htaccess con reglas de URLs amigables (qué es un .htaccess: 1.3).
Require all granted
Control de acceso: cualquier cliente puede entrar. Alternativas: Require all denied bloquea todo; Require ip 192.168.1.0/24 solo deja entrar a esa red.

⚠ No mezcles opciones con y sin signo en la misma línea (por ejemplo Options Indexes -FollowSymLinks): Apache 2.4 lo marca como error.

3.2

¿Y el 000-default.conf?

Por qué no conviene agregar un <Directory> por app dentro del sitio por defecto.

Agregar un bloque por app en sites-available/000-default.conf funciona, pero tiene tres problemas:

Se repite
cada app nueva obliga a editar el archivo del sitio, aunque las reglas sean las mismas.
Se contradice
un bloque de una subcarpeta gana sobre el de la carpeta padre. Si en uno pusiste AllowOverride None y en otro All, cada app se comporta distinto y es difícil saber por qué.
Se pierde
000-default.conf es la configuración del sitio. Las reglas de carpetas quedan más claras en un archivo aparte que se activa y desactiva con un comando.

Recomendación: quita los bloques <Directory> por app que agregaron en 000-default.conf y deja solo webapps.conf. El DocumentRoot de 000-default.conf se queda como está (/var/www/html).

$sudo nano /etc/apache2/sites-available/000-default.conf

Revisar y borrar los bloques por app que se hayan agregado.

3.3

Activar y aplicar

Cuatro comandos, siempre en este orden.

$sudo a2enconf webapps

a2enconf = Apache 2 enable conf. Crea el enlace conf-available/webapps.conf → conf-enabled/. Se escribe sin .conf. Para desactivarlo: sudo a2disconf webapps.

$sudo a2enmod rewrite

a2enmod = enable module. Activa mod_rewrite, que reescribe URLs: convierte /producto/camisa en index.php?id=15. Sin él, las URLs amigables dan error 404. Para ver módulos activos: apache2ctl -M.

$sudo apache2ctl configtest

Revisa la sintaxis de toda la configuración sin aplicarla. Debe decir Syntax OK. Si hay error, indica archivo y número de línea. Córrelo siempre antes de recargar: así un error de dedo no tumba el servidor.

$sudo systemctl restart apache2

Aplica los cambios.

reload
relee la configuración sin cortar las conexiones activas. Úsalo cuando solo cambiaste archivos .conf.
restart
detiene y vuelve a arrancar Apache. Úsalo cuando activaste un módulo con a2enmod o instalaste extensiones de PHP.
3.4

Activar HTTPS

Cifrar la conexión para todas las apps de una vez. Hazlo antes de instalar las apps.

HTTP usa el puerto 80 y el tráfico viaja en texto plano: cualquiera en la red puede leer usuarios y contraseñas. HTTPS usa el puerto 443 y Apache cifra la conexión con un certificado: una llave privada que se queda en el servidor y un certificado público que recibe el navegador.

$sudo a2enmod ssl

Activa mod_ssl, el módulo que le enseña a Apache a cifrar.

$sudo a2ensite default-ssl

Activa el sitio del puerto 443 que Debian ya trae en sites-available. Tiene el mismo DocumentRoot /var/www/html que 000-default.conf y usa un certificado de prueba («snakeoil») que el sistema generó al instalarse.

$sudo apache2ctl configtest

Debe decir Syntax OK.

$sudo systemctl restart apache2

Se activó un módulo: va restart.

Por qué aplica a todas las apps

webapps.conf y moodle.conf están en conf-enabled: esa configuración se suma a todos los sitios, al del puerto 80 y al del 443. Cada app queda disponible por las dos vías sin tocar nada más.

https://localhost/wordpress/index.php → puerto 443 → sites-enabled/default-ssl.conf → DocumentRoot /var/www/html → archivo /var/www/html/wordpress/index.php

Verificar

$sudo ss -tlnp | grep 443

Apache debe aparecer escuchando en el puerto 443.

$curl -kI https://localhost/

El -k acepta el certificado de prueba. Debe responder HTTP/1.1 200 OK (la página de bienvenida de Apache), no un error de conexión.

$sudo ufw allow 443/tcp

Solo si tienen ufw activo.

Aviso del navegador
saldrá «La conexión no es privada». Es normal: el certificado snakeoil está autofirmado. La conexión sí va cifrada, pero ninguna autoridad reconocida avala la identidad del servidor. Se acepta el aviso (Configuración avanzada › Continuar).
En producción
un servidor con dominio público usa un certificado de Let's Encrypt (gratis, con certbot). No funciona con localhost ni con una IP privada de VM.

Instala las apps con https

Cada app guarda su dirección al instalarse. Si abres el instalador con https://localhost/..., la app queda configurada con HTTPS desde el principio. Si ya las instalaste con http, la sección 7 explica cómo cambiarlas.

5. PrestaShop

5.1

Usar PrestaShop 9

PrestaShop 8 no es compatible con PHP 8.2 de Debian 12.

Descarga la versión 9 desde prestashop.com o desde la sección Releases del repositorio de PrestaShop en GitHub y guárdala en /tmp.

$cd /tmp
$sudo mkdir /var/www/html/prestashop
$sudo unzip -q prestashop_9*.zip -d /var/www/html/prestashop

El zip trae adentro otro zip y un index.php: el instalador los descomprime solo al abrirlo en el navegador.

$sudo chown -R www-data:www-data /var/www/html/prestashop
5.2

Instalar desde el navegador

Abrir https://localhost/prestashop y seguir el asistente.

⚠ Abre el instalador con la misma dirección que vas a usar siempre, con https (https://localhost o https://IP-de-la-VM). PrestaShop guarda ese dominio y después redirige todo hacia él.

Al terminar hay dos pasos obligatorios:

$sudo rm -rf /var/www/html/prestashop/install

Mientras exista la carpeta install, el back office no abre.

$ls -d /var/www/html/prestashop/admin*

El instalador renombra la carpeta admin con letras al azar (por ejemplo admin482xkq). Esa es la URL del back office: https://localhost/prestashop/admin482xkq

5.3

Solo abre el back office

La tienda (front) da 404 o página en blanco, pero el panel admin sí entra.

Causa: la tienda usa URLs amigables desde la instalación, y dependen del .htaccess. Si Apache tenía AllowOverride None o mod_rewrite apagado, el front falla.

1.
Aplica toda la sección 3 (webapps.conf, rewrite y HTTPS).
2.
En el back office: Parámetros de la tienda › Tráfico y SEO › Guardar. Esto regenera el .htaccess.
$sudo rm -rf /var/www/html/prestashop/var/cache/*

Limpiar la caché si sigue igual.

5.4

Solo abre el front

La tienda carga, pero el back office no abre o redirige a otra dirección.

URL equivocada
se está entrando a /prestashop/admin, pero la carpeta se renombró. Revisa el nombre real con el comando de 5.2.
Carpeta install
si todavía existe, bórrala (paso 5.2).
Dominio distinto
se instaló con localhost y se abre con la IP, o al revés. PrestaShop redirige al dominio guardado.

Para cambiar el dominio guardado sin entrar al back office (cambia la IP y el nombre de la base si son otros):

$sudo mysql prestashop -e "UPDATE ps_shop_url SET domain='192.168.1.50', domain_ssl='192.168.1.50'; UPDATE ps_configuration SET value='192.168.1.50' WHERE name IN ('PS_SHOP_DOMAIN','PS_SHOP_DOMAIN_SSL');"
$sudo rm -rf /var/www/html/prestashop/var/cache/*

Limpiar la caché para que tome el cambio.

6. Moodle

6.1

¿Qué versión descargaste?

Desde Moodle 5.1 cambió la estructura de carpetas.

$ls /tmp/moodle

Si ves una carpeta public, es Moodle 5.1 o posterior: sigue los pasos 6.2 y 6.3. Si no, cópialo a /var/www/html como WordPress y salta a 6.4.

En Moodle 5.1+, solo la carpeta public debe ser accesible por web. El resto (config.php con la contraseña de la base, librerías, scripts de administración) queda fuera del alcance del navegador. Si lo copias completo a html, esos archivos quedan expuestos y el sitio no carga bien.

6.2

Colocar fuera de html

Moodle va en /var/www, no en /var/www/html.

$sudo mv /tmp/moodle /var/www/moodle
$sudo chown -R www-data:www-data /var/www/moodle
6.3

Publicar con un Alias

Conectar la URL /moodle con la carpeta public.

$sudo nano /etc/apache2/conf-available/moodle.conf
# /etc/apache2/conf-available/moodle.confAlias /moodle /var/www/moodle/public
<Directory /var/www/moodle/public>
    Options -Indexes +FollowSymLinks
    AllowOverride None
    Require all granted
    DirectoryIndex index.php
    FallbackResource /moodle/r.php
</Directory>

Contenido del archivo.

Líneas nuevas respecto a webapps.conf

Alias /moodle ruta
Cuando alguien pida localhost/moodle, Apache entrega archivos de /var/www/moodle/public aunque esté fuera de html. Es un «atajo» de URL a carpeta (explicado en 1.4).
AllowOverride None
Moodle no usa .htaccess; toda su configuración de Apache va en este archivo.
DirectoryIndex index.php
Si la URL apunta a una carpeta, abre su index.php.
FallbackResource
Si la URL no corresponde a ningún archivo real (por ejemplo /moodle/course/42/manage), la manda a r.php, el «router» de Moodle, en lugar de dar 404. La ruta es de URL, no de disco: por eso lleva /moodle/ al inicio.
$sudo a2enconf moodle
$sudo apache2ctl configtest
$sudo systemctl reload apache2

Solo cambiaron archivos .conf: basta con reload.

6.4

Carpeta de datos y ajuste de PHP

Requisitos que el instalador de Moodle revisa antes de continuar.

$sudo mkdir /var/moodledata
$sudo chown -R www-data:www-data /var/moodledata

Aquí Moodle guarda archivos subidos, caché y sesiones. Va fuera de /var/www para que nunca se pueda descargar por URL.

$sudo sed -i 's/^;\?\s*max_input_vars.*/max_input_vars = 5000/' /etc/php/8.2/apache2/php.ini

Sube el límite de campos por formulario de 1000 a 5000. Moodle lo exige porque sus formularios de configuración son muy grandes.

$sudo systemctl restart apache2

Se cambió PHP: aquí sí va restart.

Directorio de datos

7. HTTPS en cada app

Apache ya sirve todo por https (paso 3.4), pero cada app guardó su dirección al instalarse. Si la instalaste con http, la app te regresa a http o carga la página sin estilos. Si la instalaste con https, solo revisa que esté así.

7.1

WordPress

Cambiar la dirección guardada a https.

Panel
Ajustes › Generales: cambiar Dirección de WordPress (URL) y Dirección del sitio (URL) a https://localhost/wordpress y guardar. WordPress cierra la sesión: vuelve a entrar ya con https.

Si después de guardar ya no puedes entrar al panel, corrige desde la terminal (base wordpress, prefijo wp_):

$sudo mysql wordpress -e "UPDATE wp_options SET option_value='https://localhost/wordpress' WHERE option_name IN ('siteurl','home');"
7.2

PrestaShop

Activar SSL desde el back office, en este orden.

1.
Parámetros de la tienda › Configuración › General.
2.
Da clic en el enlace de esa página para comprobar que la tienda abre por HTTPS. Debe cargar sin errores (aparte del aviso del certificado).
3.
Activa Activar SSL = Sí y guarda.
4.
Activa Activar SSL en todas las páginas = Sí y guarda.

⚠ Si activas SSL antes de que funcione el paso 3.4, el back office queda inaccesible. Para regresarlo a http:

$sudo mysql prestashop -e "UPDATE ps_configuration SET value='0' WHERE name IN ('PS_SSL_ENABLED','PS_SSL_ENABLED_EVERYWHERE');"
$sudo rm -rf /var/www/html/prestashop/var/cache/*

Limpiar la caché para que tome el cambio.

7.3

Moodle

Moodle guarda su dirección en config.php, no en el panel.

$sudo nano /var/www/moodle/config.php
# /var/www/moodle/config.php (línea wwwroot)$CFG->wwwroot   = 'https://localhost/moodle';

Solo cambia http por https en esa línea.

Moodle acepta una sola dirección. Si alguien entra con otra (http, o la IP en lugar de localhost), Moodle lo redirige a la que diga wwwroot. No hace falta reiniciar Apache: config.php se lee en cada petición.

7.4

Forzar HTTPS siempre

Opcional y al final: mandar todo lo que llegue por http al puerto 443.

⚠ Hazlo solo cuando las tres apps ya funcionen por https. Si no, se forman ciclos de redirección (http → https → http…).

$sudo nano /etc/apache2/sites-available/000-default.conf
# dentro de <VirtualHost *:80>, antes de </VirtualHost>RewriteEngine On
RewriteCond %{HTTPS} off
RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [R=301,L]
RewriteCond %{HTTPS} off
«si la petición NO llegó cifrada…»
RewriteRule ^ https://…
«…mándala a la misma dirección, pero con https». %{HTTP_HOST} conserva lo que escribió el usuario (localhost o la IP) y %{REQUEST_URI} conserva la ruta (/wordpress/index.php).
[R=301,L]
301 = redirección permanente; L = no evaluar más reglas.
$sudo apache2ctl configtest
$sudo systemctl reload apache2

Solo cambió un .conf: basta con reload.

Diagnóstico rápido: apache2ctl -S muestra los sitios activos, apache2ctl -M | grep rewrite confirma mod_rewrite y ls /etc/apache2/conf-enabled lista las configuraciones encendidas.
